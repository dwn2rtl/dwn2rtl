# Phase 7 ledger — harden it, then ship the fixes

**Goal.** Find every way the tool can be broken by a user, fix them, and get the fixes to the
people who have the broken version.

**Status: CLOSED.** Retrospective in `phase7-report.md`.

> Conventions in `overview.md` §6. Entries oldest first, recording *built* / *hit* / *decided*.
> Reversed decisions stay, struck through, with the reason.

---

## The rule this phase is organised around

**Stop adding cases; start measuring whether the existing ones can fail.** Seven rounds of
adversarial input had decayed into finding message-quality issues, which is the signal that
hand-picked tests have run out of imagination -- not that the tool is correct.

The techniques that replaced it -- coverage, then mutation testing -- measure the *tests* rather
than the tool, and each found defects that manual auditing had walked past for a whole session.

The full round-by-round record lives in `phase6-ledger.md` §10-29; this ledger picks up at the
point where hardening turned into a release.

---

## 1. Built — every generated file says which version wrote it

The 0.2.0 rename of `pipe_reg`'s parameter from `ENABLE` to `STAGES` is technically breaking in
one narrow way: a user who updates the generated files but keeps 0.1.0's primitives gets
`Parameter not found: STAGES`.

**Decided: no compatibility shim.** The mismatch cannot produce a wrong design -- Verilog refuses
to elaborate -- and it cannot happen through normal use, because `build` copies every primitive
fresh on each run. Aliasing the parameter would mean two names that must agree, and keeping the
old name would preserve the misleading word that caused the bug.

⚠️ **What was genuinely wrong is that the error was undiagnosable.** Emitted files said
`GENERATED by dwn2rtl` with no version, so nothing told a user their primitives were older. Now:

```
// GENERATED by dwn2rtl 0.2.0 -- do not edit by hand.
```

on every generated `.v` and `.vh`. The hand-written primitives stay unstamped because `build`
copies them as BYTES -- deliberately, so Windows cannot rewrite their line endings -- and the
`.hex` files stay unstamped because `$readmemh` parses values, not comments. Both halves of that
are pinned by a test.

## 2. Built — 0.2.0, and the first CHANGELOG

`0.1.0` shipped with the vector-packing defect, so every day it stayed current was a day the
published tool reported `core FAIL` on correct designs whose thermometer width was not a multiple
of 8. That made the release a fix rather than a feature drop.

A changelog became worth having at the second release, and it leads with the upgrade reason
rather than a feature list.

⚠️ **The README link test caught the changelog before CI did.** Adding the link while the file
was still untracked reproduced exactly the defect that test was written for -- a README pointing
at something that does not exist on GitHub. It failed, correctly, until the file was staged.

## 3. 🎯 Two CI jobs ran for the first time, and one found a real defect immediately

macOS had been listed as supported since the first release and **had never once executed**. The
declared floors -- `numpy>=1.22`, `torch>=2.0` -- had never been installed either, because every
run resolved to the newest release.

Building the floor environment broke on contact:

```
numpy 2.4.6 | torch 2.0.1  ->  209 failed
RuntimeError: Numpy is not available
```

⚠️ **Our own metadata permitted a combination that cannot work.** torch builds before ~2.3 were
compiled against NumPy 1.x and cannot hand a tensor to NumPy 2 at all, and every emitter reads
tensors through `.numpy()`. The two constraints are each satisfiable while being mutually
incompatible -- and since pip resolves numpy to the newest release, **anyone holding an older
torch got the broken pair by default.**

**Measured before choosing a fix:** torch 2.0.1 with numpy 1.26 passes the entire suite. Raising
the torch floor would therefore forbid a combination that works, in order to prevent one that pip
produces by accident. So the pairing is detected once, at the load entry points, and explained
with both ways out. Verified in a genuinely broken environment on the path a real user takes:
save a checkpoint from a healthy install, load it from the broken one.

Both jobs passed on their first real run at release time.

## 4. Built — the release, and verified on the index rather than assumed

Published through the existing Trusted Publishing workflow: `build` -> `gate` + `verify` ->
`publish`, so nothing uploads unless the suite passes AND the built wheel installs with no source
tree and drives a simulator to PASS.

⚠️ **Then verified from PyPI itself**, because a green publish job proves the upload succeeded,
not that the artifact is the one we think it is:

| | |
|---|---|
| `pip install dwn2rtl`, no flags | `dwn2rtl-0.2.0`, provenance attestations present |
| import origin | site-packages, not the repo |
| `quickstart.py` | core 504 ✓, top 535 ✓, **PASS** |
| **odd width (6x3 = 18)** | **core PASS** -- this was `core FAIL` in 0.1.0 |
| **`Pipeline(lut=2)`** | **PASS** -- silently one register in 0.1.0 |
| **zero latency** | **PASS** -- mis-sampled in 0.1.0 |

Tagged `v0.2.0` at the exact published commit, after publishing rather than before, so the tag
records what actually shipped.
